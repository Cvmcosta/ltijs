# ltijs TypeScript Port — Plan & Status

This document is the authoritative, living reference for the ongoing TypeScript port of ltijs. It's meant to survive across sessions/context windows — read this first when picking the port back up. Update it whenever a round of work finishes or a standing convention changes.

The legacy CommonJS/Babel source (`src/Provider/`, `src/Utils/`) is **untouched and still fully working** throughout this port — nothing here has broken it; `src/index.ts` still exports it directly and it remains the actual published package's runtime until the port cuts over. The legacy Mocha test suite (`test/*.js`) was removed once the new suite's coverage was confirmed to meet or exceed it (see Round 77) — the legacy *source* stays until the cutover, only its tests and their tooling (`mocha`/`nyc`/`chai`/`nock`/`cheerio`) are gone. The TypeScript port lives alongside the legacy source in `src/services/`, `src/utils/`, `src/shared/`, and is not wired into the legacy code yet.

## Goal

Port ltijs to TypeScript with real typing, replacing `got` with `axios` and adopting Zod for schema/type/validation — modernizing the codebase in preparation for future improvements, while keeping the public API (`require('ltijs').Provider` and its documented methods/error strings) as close to today's as possible.

## Standing conventions

These apply to all future work, not just the module being ported at the time:

- **Tooling**: mirrors the sibling SDK at `/Users/cvmcosta/Desktop/cvm/code/ltiaas/sdks/ltiaas-node` in spirit (`eslint-config-love` + Prettier, Husky + lint-staged) but has since diverged on the build/alias mechanism specifically — see below.
- **Node engine floor bumped to `>=24`** (was `>=18`; `@types/node` bumped to match, `^24.13.3`, replacing the previously-mismatched `^22.7.5`). This is a deliberate divergence from the sibling `ltiaas-node` SDK, which still targets `>=18.12.1` — not something this port is "catching up" on, a new precedent set here. Confirmed low-risk before applying: no Node-version-gated code anywhere in `src/`/`test/`/`scripts/`, no native addons in the dependency tree, and every runtime dependency's own `engines` field is a permissive floor well under 24. One initially-suspected action item (three call sites thought to use Node's deprecated `url.parse()`) turned out to be a false positive — `Provider.js`/`DynamicRegistration.js` both alias the third-party `fast-url-parser` package to a variable named `url`/`_url`, not Node's core `url` module, so nothing needed changing there. A `.nvmrc` (`24`) pins this for local dev/CI.
- **TypeScript devDependency runs the official 7.0 side-by-side split, not a single version.** `typescript` (the local package name) is aliased to `npm:@typescript/typescript6@^6.0.2` — this is what every `require('typescript')`/peer-dependency consumer (`ts-jest`, `ts-node`, `eslint-config-love`/`typescript-eslint`) resolves, so they keep running unmodified on the full, stable, JS-hosted Compiler API. A second devDependency, `typescript-native`, is aliased to `npm:typescript@^7.0.2` (the real Go-native package) and is what `build:compile` invokes explicitly (`node_modules/typescript-native/bin/tsc -p tsconfig.build.json`), so the actual build/type-check step gets 7.0's real speedup. This split exists because TypeScript 7.0 ships with no public Compiler API at all (it returns in 7.1, undated as of 2026-08) — every tool above needs that API and can't run on 7.0 directly. Revisit collapsing both entries back into one plain `"typescript": "^7.1.x"` once 7.1 ships and `ts-jest`/`ts-node`/`typescript-eslint` confirm direct support. As a consequence of the underlying TS 6.0 baseline, `tsconfig.json` has no `baseUrl` (removed; `paths` entries are relative to the tsconfig file itself), sets `"rootDir": "."` explicitly (6.0 changed the default from auto-inferred, and the base config's `include` spans files both inside and outside `src/`), and declares `"types": ["node", "jest"]` explicitly (6.0 changed the default from auto-including every visible `@types/*` package to an empty array).
- **Path aliases are `#`-prefixed Node subpath imports (`#/*`, `#provider/*`, `#services/*`, `#utils/*`, `#shared/*`, `#test/*`), declared exactly once, in `package.json`'s `"imports"` field, with a `development`/`default` condition pair — not `@`-prefixed `tsc-alias`-rewritten ones, and not a separate `tsconfig.json` `paths` declaration either.** `tsc-alias` has been removed from the build entirely. Each alias is one conditional entry, e.g. `"#services/*": { "development": "./src/services/*.ts", "default": "./dist/services/*.js" }` (`#test/*` has no `"default"` — test files are excluded from the build and never reach `dist/`, so it's only ever resolved under the `development` condition anyway). Three consumers each activate `development` their own way, with **zero duplicated alias declarations**: `tsconfig.json` sets `"customConditions": ["development"]` (no `paths` field at all — TS's own `Node16` resolution reads `package.json` `imports` directly); `jest.config.ts` sets `testEnvironmentOptions: { customExportConditions: ['development'] }` (no `moduleNameMapper`, no `pathsToModuleNameMapper` import from `ts-jest` — Jest's own resolver honors the same conditional `imports` map); real `node dist/...` execution has no custom condition active, so it falls through to `"default"`, resolved natively with no rewriting. Adopted from a reference boilerplate (`/Users/cvmcosta/Desktop/cvm/code/resources/ts-boilerplate`) after verifying the mechanism end-to-end in an isolated prototype mirroring ltijs's exact shape (multiple aliases plus the test-only, build-excluded `#test/*` case) *before* touching the real config, then re-verified after (full `build`/`test`/`lint` pass, plus a direct `node -e "require('./dist/...')"` check that the real compiled output's `require("#services/...")` genuinely resolves via the `default` condition).
- **CI**: `.github/workflows/ci.yml` runs on Node 24 (`.nvmrc`), `npm ci`, an explicit check that `node_modules/typescript` resolves to a 6.x version and `node_modules/typescript-native` to a 7.x version (the split's load-bearing assumption), then `npm run test` and `npm run build`. This is the repo's first real CI — previously only a stale, unused `.travis.yml` (`node_js: "11"`) existed. **Known, pre-existing gap this immediately surfaces, not introduced by any of the above**: `npm run check:lint` (part of `npm run test`) currently fails on 8 real `@typescript-eslint/no-unsafe-*` errors in `platform-manager.service.test.ts`, caused by the test calling four methods (`deletePlatformById`, `setPlatformActive`, `getPublicKey`, `getPrivateKey`) that don't exist on `PlatformManager` today (confirmed via `tsc --noEmit`) — a real implementation/test drift, not a CI or tooling artifact. CI will be red on this until that drift is resolved as its own piece of work.
- **`RequestHandler`'s pluggable interface (`request-handler.types.ts`) returns its own `RequestResponse<T>` (`{ data: T, headers: Record<string, string | undefined> }`), not the concrete `AxiosResponse<T>`.** The interface previously leaked axios's own response type despite being documented as a swappable, framework-agnostic contract (the same shape as `DatabaseManager`/`HttpHandler`) — caught while adding a second implementation, `FetchRequestHandler` (`services/request-handler/fetch/`, mirroring `services/request-handler/axios/`'s file layout per the established pluggable-implementation-subfolder convention), which couldn't plausibly return a real `AxiosResponse` without fabricating one. `RequestResponse`'s two fields are the complete set any real consumer touches today (`.data` almost everywhere; `NamesAndRoles` also reads `.headers.link` for Link-header pagination) — confirmed by checking every actual call site before narrowing the type, not assumed. `AxiosRequestHandler` now maps its real `AxiosResponse` into this shape at each method; `FetchRequestHandler` builds it directly from a native `Response`. Both implementations exist side by side deliberately — `axios` is not being replaced, per explicit instruction; `got` → `axios` (already documented above) remains the only HTTP-client migration actually in flight.
- **Devdependency versions are kept aligned with the reference boilerplate (`/Users/cvmcosta/Desktop/cvm/code/resources/ts-boilerplate`) where its version is strictly newer** — `@types/jest` (`^30.0.0`), `del-cli` (`^7.0.0`), `husky` (`^9.1.7`), `jest` (`^30.4.2`, a major bump from `^29.7.0`), `lint-staged` (`^17.3.0`), `prettier` (`3.9.6`), `ts-jest` (`^29.4.12`). Verified `ts-jest@29.4.12`'s own `peerDependencies` before bumping Jest across a major version: it declares `jest: '^29.0.0 || ^30.0.0'` and `typescript: '>=4.3 <7'` — both bumps are genuinely supported, not a fluke, and the `typescript: <7` peer range is exactly why `ts-jest` needs to keep resolving the local `typescript` name to the 6.0 alias, never the `typescript-native` one. **`@types/node` was deliberately *not* bumped to match** (the boilerplate uses `^26.2.0`, itself ahead of its own `engines: >=24`) — ltijs's `@types/node` is intentionally pinned to match its actual `engines` floor (`^24.13.3`), and blindly copying "newer" here would reintroduce the exact types/engines mismatch that was fixed earlier. One real Jest 30 breaking change surfaced by this bump: `jest.dbconfig.ts`'s `import baseConfig from './jest.config'` (no extension) stopped resolving — Jest 30 apparently loads TS config files with genuinely stricter resolution than 29 did. Fixed by adding an explicit `.ts` extension (`'./jest.config.ts'`); a `.js` extension (the usual `Node16`-convention choice for relative imports) did *not* work here, since jest.config.ts is a source file consumed directly, not part of `tsc`'s compiled output.
- **Zod** for schema/type/validation: `<module>.schemas.ts` (Zod schemas, PascalCase + `Schema` suffix) + `<module>.types.ts` (`z.infer`-derived types, same name minus `Schema`), validated through the shared `validate<T>(schema, value)` helper (`src/utils/validation.ts`).
- **Types are always declared in a `<module>.types.ts` file — never inline inside a `.service.ts`/`.serializer.ts`/other implementation file, no matter how small or seemingly private to that file.** Caught when `id-token.serializer.ts` had defined four small claim-payload interfaces (`ToolPlatformClaim`, etc.) locally, purely to back its own `as` casts -- moved into a new `id-token.types.ts` per explicit instruction, with the serializer importing them like any other type. This applies even to a type with exactly one consumer: the file-kind boundary (`.types.ts` holds types, `.service.ts`/`.serializer.ts` hold logic) is the rule, not "is this type reused elsewhere."
- **A nested section of a type that's substantial enough to be referenced elsewhere (a function return type, a parameter type, another interface's field) gets its own named interface, not an inline nested object type reached via lookup syntax (`IdToken['user']`, `NonNullable<LegacyIdToken['platformContext']>['resource']`).** Caught per explicit instruction, disliking the `Type['field']` convention -- `IdToken`'s `user`/`platform`/`launch`/`services` sections (plus `launch.presentation` and each of `services`'s three sub-shapes) became their own named interfaces (`IdTokenUser`, `IdTokenPlatform`, `IdTokenLaunch`, `IdTokenLaunchPresentation`, `IdTokenNamesAndRolesService`, `IdTokenAssignmentAndGradesService`, `IdTokenDeepLinkingService`, `IdTokenServices`), and likewise for `LegacyIdToken`'s `platformContext` section (`LegacyIdTokenPlatformContext`, `LegacyIdTokenResource`, `LegacyIdTokenNamesRoles`). `id-token.serializer.ts`'s per-section builder functions (`buildUserInfo` etc.) and casts now reference these named types directly (e.g. `function buildUserInfo(record): IdTokenUser`) instead of indexing into the parent type. A trivial inline object type with no independent meaning (e.g. a two-field ad hoc shape used nowhere else) doesn't need this -- the rule is for a section substantial/reusable enough to be worth naming and referencing from elsewhere, not every nested object literal type.
- **`utils/` holds plain function modules only — never classes.** (Physically lives at `src/shared/utils/` as of Round 48, still reached via the unchanged `@utils/*` alias -- see the `services`/`shared` split note further down.) Any class — user-facing business logic or lower-level shared machinery alike — belongs under `services/` with a `.service.ts` file-name suffix (e.g. `services/request-handler/axios/axios-request-handler.service.ts`). `utils/` is reserved for genuinely plain functions: `validation/validation.ts`, `request/link-header.ts`, `random/random.ts`, the `crypto/` module (pure cryptographic primitives -- key generation, JWT decode/verify/sign, JWK↔key conversion; no `DatabaseManager`/platform/claim knowledge at all, unlike the `OidcService` class that calls into it).
- **Types must be pure data, with no methods.** Whenever a domain concept needs both data and behavior, split it into a plain type (e.g. `Platform` in `services/platform-manager/platform-manager.types.ts`) plus a service that receives/returns that type and performs all operations on it (e.g. `PlatformManager`). Don't bundle behavior into the type.
- **Services are classes**, not factory functions — this gives real dependency-injection benefits (injecting `RequestHandler`, a database interface, eventually a logger). Within a class, keep public methods short by decomposing into well-named `private` helper methods.
- **TypeScript's `private`/`public`/`readonly` keywords**, not native `#field` syntax — a deliberate, accepted behavior change from the legacy JS (native `#fields` are invisible to `JSON.stringify()`/reflection at runtime; TS `private` is compile-time-only and leaves fields enumerable). Chosen for consistency with the `ltiaas-node` reference SDK and readability.
- **No default constructor parameters for injected dependencies, anywhere.** Every constructor dependency (`DatabaseManager`, `RequestHandler`, `Logger`, `PlatformManager`, `AccessTokenManager`, `GenerateKeyPairFn`) is a plain required parameter, just stored as `private`/`readonly` — never `= someSharedDefault`. No module exports a pre-built shared singleton instance of a service class either (`AxiosRequestHandler`/`DefaultLogger` export only their class). Wiring real implementations together is the job of a centralized construction point, not yet built (`TBD`) — until it exists, callers (including tests) construct and pass every dependency explicitly. This also means a service that itself composes other services (e.g. `NamesAndRoles` needing a `PlatformManager` and an `AccessTokenManager`) takes those **already-constructed** instances directly as constructor params, rather than taking their raw ingredients (e.g. a `DatabaseManager`) and building its own private copies internally — avoids redundant, un-shared instances of the same service. **Exception (Round 42), narrowly scoped**: the raw framework instance underlying a pluggable interface's own concrete implementation (`AxiosInstance` inside `AxiosRequestHandler`, `Express` inside `ExpressHttpHandler`) is that class's own implementation detail, not a swappable dependency a consumer supplies — a consumer who wants different behavior there depends on the `RequestHandler`/`HttpHandler` *interface* and supplies a different concrete class, rather than reaching into one implementation's internals. Both now build their own framework instance internally with no constructor param for it at all (not customizable yet — a future options param is explicitly deferred, not designed here).
- **Pluggable cross-cutting concerns are interfaces with a concrete implementation**, the same shape as `DatabaseManager`/`MongoDatabaseManager`: `RequestHandler` (interface, `request-handler.types.ts`) / `AxiosRequestHandler` (implementation), `Logger` (interface, `logger.types.ts`) / `DefaultLogger` (implementation, wraps the `debug` package). Consuming services depend on the interface type; an instance of the concrete implementation is passed in explicitly (see above -- never defaulted).
- **No magic strings for log levels or component names.** `Logger` has one method per level -- `debug(component, message)`, `warn(component, message)`, `error(component, message)` -- so the level is which method you call, not a string argument (there's no `LogLevel` type or level parameter to typo). Every service that logs owns its component name as a `private readonly LOG_COMPONENT` class field (e.g. `private readonly LOG_COMPONENT = 'platformManager'`) -- never a module-level constant sitting outside the class, and never a string literal repeated inline at each call site.
- **Service-internal constants are `private readonly` class fields, not module-level constants.** A `const` sitting above a class (e.g. `NRPS_SCOPE`, `CLIENT_ASSERTION_TYPE`) belongs inside the class as `private readonly` instead, unless something outside the class genuinely needs it -- in which case it's a `public readonly` field (or a real exported constant, if it's not tied to one specific service at all).
- **No magic strings for values compared against, switched on, or assigned as a fixed protocol/business constant -- extract a named `private readonly` class field (or a shared enum, if the value is genuinely reused across services/schemas) instead of a bare string literal.** Introduced explicitly in Round 30, applied as a sweep across `OidcService`, `NamesAndRoles`, `PlatformManager`, `AxiosRequestHandler`, `AccessTokenManager`, and `MongoDatabaseManager`. Covers OIDC protocol constants (`response_type`/`response_mode`/`scope`/`prompt` values in `OidcService.buildAuthenticationRequestQuery()`), the required LTI version string (`'1.3.0'`), NRPS query-param names (`role`/`limit`/`rlid` in `NamesAndRoles`), HTTP header names (`Authorization`/`Accept`/`Content-Type` in `AxiosRequestHandler`), OAuth2 grant-type/JWT-algorithm values (`AccessTokenManager`), Mongoose connection-lifecycle event names (`MongoDatabaseManager.setup()`), and Zod `ValidationError` issue-path strings used for dispatch (`PlatformManager`'s `idtokenValidation.method`/`.key` paths). **Explicitly excludes error-message strings passed to `new Error(...)` and log messages passed to `logger.debug/warn/error`** -- those stay literal text, per direct instruction; this rule is about values a comparison/switch/protocol build actually depends on, not human-readable copy. A single-use, self-evident literal with no risk of drifting out of sync with itself (e.g. `'?'` in `LaunchService.splitTargetLinkUri()`'s `indexOf('?')`, universal URL syntax, not a domain constant) doesn't need extraction either -- the rule targets literals that are meaningful, protocol-defined, or duplicated, not every string in the codebase. When the *same* value is genuinely shared across multiple files (not just conceptually similar), it becomes a shared enum per the `<domain>.constants.ts` convention above rather than independent per-service fields (see `AuthConfigMethod`, below) -- but a coincidentally-identical value used for unrelated reasons in two different services (e.g. `RS256` as `OidcService`'s ID-token-verification algorithm vs. `AccessTokenManager`'s client-assertion-signing algorithm) is fine as two independent `private readonly RS256` fields, since centralizing it would imply a shared meaning that doesn't actually exist.
- **Typed `LtijsError` hierarchy, replacing bare `throw new Error('STRING')` everywhere a service/util already threw a specific legacy-preserved error.** A shared `LtijsError` (`src/shared/errors.ts`, moved from `errors/ltijs-error.ts` in Round 45) extends `Error`, taking just a `message` and setting `this.name = new.target.name` so every subclass automatically gets its own name with no repeated `this.name = 'X'` boilerplate. Each service/util owns its own colocated `errors.ts` (e.g. `services/lti/oidc/errors.ts`) defining one class per distinct error string it throws, each `extends LtijsError` with a **no-arg constructor** hardcoding its own fixed message (`super('EXACT_LEGACY_STRING')`) -- call sites change from `throw new Error('X')` to `throw new XError()`. **Deliberately no active logging inside `LtijsError` itself** -- the original idea was for the base class to log itself when constructed, but `Logger` is constructor-injected per-service (no singletons, per the DI convention above) and a bare `throw new SomeError()` call site has no natural access to one; confirmed with the user, logging (if ever added) would happen wherever an error is actually caught, not automatically at construction/throw time. **No class is ever shared across two services even when their message strings are identical** (e.g. `platform-manager`'s and `access-token-manager`'s independent `PrivateKeyNotFoundError`s) -- same reasoning as the `RS256` precedent above: centralizing would imply a shared meaning that doesn't actually exist. Introduced in Round 36, applied to `PlatformManager`, `OidcService`, `LaunchService`, `NamesAndRoles`, `AccessTokenManager`, `MongoDatabaseManager`; **deliberately deferred**: `Grading`/`DeepLinking`/`DynamicRegistration` (still red `NOT_IMPLEMENTED` stubs) and `shared/utils/crypto/` (a pure, dependency-free module set, not a "service"). `ValidationError` (see below) is the one error class that isn't a fixed-message no-arg constructor, since it's built from a runtime `ZodError`.
- **Pluggable HTTP routing is an interface + concrete implementation, the same shape as `DatabaseManager`/`MongoDatabaseManager`**: `HttpHandler` (interface, `services/http-handler/http-handler.types.ts`) / `ExpressHttpHandler` (implementation, `services/http-handler/express/`). A `RouteHandler` receives a framework-agnostic `HttpRequestParameters` (already-parsed `query`/`body`/`cookies`/`headers`, never a raw framework `Request`) and an imperative `HttpResponse` object (`status`/`setCookie`/`clearCookie` return `this` for chaining, mirroring Express's own `res`; `redirect`/`html`/`json` are terminal) -- itself an interface, implemented per-framework by its own class (`ExpressHttpResponse`), constructed fresh per request. Introduced in Round 37.
- **A pluggable service's framework-/implementation-specific code lives in its own eponymous subfolder under that service's directory, mirroring `services/database-manager/mongo/`.** `services/http-handler/`'s shared, framework-agnostic `http-handler.types.ts` interface sits at the service root; every Express-specific file (`ExpressHttpHandler`, `ExpressHttpResponse`, their tests, the Express middleware wiring) lives under `services/http-handler/express/` instead -- confirmed via explicit correction when an initial draft put them directly in `services/http-handler/` alongside the interface. A future second implementation (e.g. a Fastify one) would get its own sibling subfolder, never sharing files with `express/`, exactly like `mongo/`/`mongo-legacy/` each own independent schema/service modules.
- **Every `utils/` file lives in its own topic subfolder, not flat in `utils/`.** Confirmed via explicit correction on `utils/template-renderer.ts` (moved to `utils/http/template-renderer.ts`, later `utils/templating/`) -- matches how `utils/crypto/` and `utils/validation/` were already topic subfolders rather than flat files. Originally scoped to new files only, with the remaining flat files (`http-client.ts`, `link-header.ts`, `authorization.ts`, `encryption.ts`) left in place -- but the user retroactively applied the same treatment to those too in Round 41 (`utils/request/` now holds `http-client.ts`/`link-header.ts`/`authorization-header.ts`, `encryption.ts` became `utils/crypto/aes-encryption.ts`), so there's no flat exception left standing. A single-concern module gets split by concern the same way a file grows past one responsibility: `utils/crypto/crypto.ts` (JWT decode/verify + JWK/key conversion + platform-key generation, three distinct concerns sharing one file) split in Round 48 into `jwt.ts` (JWT operations, including a new `signJwt()` wrapping `jsonwebtoken`'s own `sign()`, matching `verifyTokenSignature()`'s existing "don't call the library directly from a service" precedent) and `keys.ts` (`jwkToKey`/`generatePlatformKeyPair`), each with its own test file; a service or util's random-identifier generation likewise consolidates into `utils/random/random.ts` (Round 49) rather than each call site invoking `node:crypto`'s `randomUUID()`/`Math.random()` directly.
- **`services/` splits into a `lti/` subfolder (per-launch orchestration and platform-registration flows: `oidc`, `launch`, `names-and-roles`, `grading`, `deep-linking`, `dynamic-registration`) and everything else flat at `services/` root (reusable cross-cutting infrastructure: `database-manager`, `platform-manager`, `access-token-manager`, `request-handler`, `http-handler`, `logger`).** Introduced in Round 48, per explicit instruction -- a `services/shared/` subfolder for the infrastructure half was tried in the same round and reverted immediately, on the reasoning that "services are by definition shared": every service in this port is already a reusable, DI-friendly class with no hidden global state, so a `shared/` qualifier on top of that added a label without adding information: the real distinguishing fact is which services are *LTI-launch-scoped* (`lti/`) versus generically reusable (root), not which ones are "shared" (all of them are). `src/shared/` (the top-level directory, distinct from this) is a different, older concept -- non-service code with no service-shaped home at all (`LtijsError`, `PlatformLike`/`GetPlatform`, and as of Round 48 the whole `utils/` tree) -- and was unaffected by this decision.
- **A per-launch/per-request-flow service that wires real HTTP routes takes its `HttpHandler` as a constructor dependency (not a per-call method param) and gets a `prepareHttpRoutes(onX: OnXHandler, routes?: XRoutes)` method**, registering its own routes onto that constructor-injected `HttpHandler` -- established in Round 37 as `LaunchService`'s own HTTP wiring, the reference example for `Grading`/`DeepLinking`/`DynamicRegistration` to follow once each needs the same treatment; `httpHandler` moved from a `prepareHttpRoutes()` parameter to the constructor in Round 39, per explicit instruction, matching every other cross-cutting dependency's DI shape in this port. The route-path DTO (`LaunchRoutes`, mirroring `DynamicRegistrationRoutes`) is a plain method-parameter default (not a `= someSharedDefault` constructor dependency, so it doesn't conflict with the "no default constructor params for injected dependencies" rule above), and the caller-supplied `onX` handler is that one method's own extension point, not a global callback registry -- `Provider` core's full `onSessionTimeout`/`onInvalidToken`-style registry is still separate, deferred work. **The methods each route delegates to (`processLogin()`/`processLaunch()`) are `private`**, per an explicit same-round correction: since they're only ever reached through the routes `prepareHttpRoutes()` itself registers, there's no reason for them to be a separate public surface, and each route handler validates its own input (via a Zod schema) *before* calling into its now-fully-trusting private method, rather than that method re-validating its own params. `getLaunchContext(id)` stays `public`, since it's a session-resumption entry point not reached by any route `prepareHttpRoutes()` registers.
- **Jest**, replacing the legacy mocha/chai/nock suite. HTTP calls are mocked with `axios-mock-adapter`; `mongodb-memory-server` is kept for real Mongoose DB integration tests (`*.dbtest.ts`, run via `jest.dbconfig.ts`) — this matters because third-party ltijs database plugins (`ltijs-firestore`, `ltijs-sequelize`) depend on the DB layer's real behavior, not just its type shape.
- **Red/green, test-first workflow** for modules not yet implemented: write a fully-typed class stub (correct constructor/method signatures, bodies `throw new Error('NOT_IMPLEMENTED')`) plus a complete Jest suite asserting the *real* intended behavior (translated from the legacy mocha coverage) — genuinely red until implemented. This is deliberate so the team can be confident everything is correctly implemented before release, rather than discovering gaps after the fact. **Tests must assert real intended behavior, not the stub's `NOT_IMPLEMENTED` placeholder** — a test that asserts `.rejects.toThrow('NOT_IMPLEMENTED')` is testing the stub, not the target behavior, and won't naturally go green when the method is implemented.
- **A service-specific `ensureServiceAvailability(idtoken)` guard, called first in the public entry method, fails fast before any platform/token work.** `NamesAndRoles.getMembers()` establishes the pattern: `idtoken` is a required param (not `IdTokenRecord | undefined`), and the method throws the service-specific "not available" error (e.g. `MISSING_NAMES_ROLES_SERVICE_URL`) the moment the relevant LTI namespaced claim is missing from the raw record, before `resolveActivePlatform()`/`getAccessToken()` do any real work. The guard body reads `idtoken?.[CLAIM_KEY]` (the `idtoken?.` is defensive against non-TS-compliant callers, not the type system, and needs a `no-unnecessary-condition` eslint-disable). This intentionally drops the separate legacy `MISSING_ID_TOKEN` check other services still had -- a missing/malformed `idtoken` now surfaces as the same service-unavailable error, since `NamesAndRoles` (and its siblings) are internal services invoked only after session validation, not a system boundary themselves. Apply the same shape to `Grading`/`DeepLinking`/`DynamicRegistration` when each is actually implemented. (`idtoken` was originally the formatted `IdToken`, reading `idtoken.platformContext?.<claim>` -- switched to the raw `IdTokenRecord` in Round 23, see below.)
- **No per-call `DatabaseManager` override param anywhere a service already has one injected.** `PlatformManager.getPlatform()`/`registerPlatform()` used to accept an optional `databaseManager` argument overriding the constructor-injected one; this was a legacy workaround for `Provider.getPlatform` being passed around as an unbound function reference, which a constructor-injected, properly-bound `PlatformManager` never needs. Removed entirely rather than kept for hypothetical flexibility.
- **Three-layer record model for pluggable storage** (`DatabaseManager`/`MongoDatabaseManager`/`MongoLegacyDatabaseManager` is the reference example): (1) **service level** -- formatted, backward-compatible public types (e.g. `Platform`, `PlatformRegistrationInput`) that keep both old and new field names live simultaneously when a field is renamed (e.g. `accessTokenEndpoint`/`accesstokenEndpoint`, `idtokenValidation`/`authConfig` -- same value, resolved via an `input.newName ?? input.oldName`-shaped helper); (2) **interface record level** (`database-manager.types.ts`) -- plain hand-written types, no Zod, no schema/validation, no implementation-specific structure, just what a service needs to build its formatted type; database-structure concerns (does status live in its own table? are keys their own collection?) never leak up into this layer -- a status/key set that's naturally part of the same conceptual entity as its parent (e.g. a platform's `active` flag and its keys) is a plain field on that entity's record, even if one implementation happens to store it in a separate table. (3) **implementation record level** (e.g. `mongo/database-schemas.ts`) -- whatever a concrete database actually stores; each implementation owns its own Zod validation against its own document shape (`mongo/mongo-database-manager.schemas.ts`), then serializes/deserializes to and from the interface's records. **`mongo/` and `mongo-legacy/` are fully isolated implementations -- zero imports between them in either direction, as if either could be extracted into its own package** (tightened in Round 54: `MongoLegacyDatabaseManager` no longer `extends MongoDatabaseManager`, and even the one thing they used to import from each other -- two shared collection-name constants -- is now each side's own local literal instead). Every implementation-specific piece a pluggable storage backend needs (Mongoose schema/model module, Zod validation schemas, connection-config type, error classes, connection-lifecycle logic) is duplicated independently per implementation, never shared, even when the content is identical between them (e.g. both `errors.ts` modules define byte-identical `MissingDatabaseConfigError`/`ProviderNotDeployedError` classes -- two classes, not one imported twice). The only thing genuinely shared between `mongo/` and `mongo-legacy/` is the top-level public interface both conform to (`DatabaseManager`, `PlatformRecord`, etc. in `database-manager.types.ts`) -- that's the actual abstraction boundary, not an implementation detail. Where two implementations' models target the exact same real, physical MongoDB collection name (e.g. `platforms`), that's an intentional *runtime* characteristic (both must be able to coexist against one real deployed database during a migration), declared independently as each side's own local string literal, not imported -- and where a plain unique index on a field one implementation always sets but the other never does would otherwise cause a null-collision between the two implementations' incompatible documents sharing that collection, the index needs a `partialFilterExpression` excluding documents missing that field (a no-op for the implementation whose own field it is). A legacy implementation constrained to a real, already-deployed schema (`MongoLegacyDatabaseManager`) does real merge-on-read/decompose-on-write work across multiple collections to satisfy a unified interface record; it isn't required to make every interface field perfectly round-trip if the legacy schema structurally can't support it (see `IdTokenRecord`'s `aud`/`exp`/`iat`/`nonce` below).
- **MongoDB/Mongoose field names must never contain a literal dot when queried by that name.** Both Mongoose's Document/path layer (even with `strict: false`) and MongoDB's own query-filter syntax always interpret a dot in a field name as nested-path notation, not a literal character -- writing a flat field like `'https://.../claim/x'` at the top level can silently split into nested sub-documents (Mongoose), and even when written correctly via the native driver (bypassing Mongoose's Model/Document API), querying by that same dotted key never matches via a standard filter (MongoDB). Any field genuinely needed for a query/index (not just storage) must have a clean, dot-free name.
- **Never derive a "record minus one field" input type via `Omit<Interface, 'field'>` when `Interface` also has a string index signature (e.g. `IdTokenRecord`'s `[claim: string]: unknown`).** TypeScript's mapped-type machinery (`Omit`/`Pick`) collapses every named property down to the index signature's type in that case, and worse, spreading a value of that `Omit<>`'d type (`{...token, id}`) loses the named properties entirely -- the spread only carries forward what was explicitly re-added. Confirmed via an isolated repro during the launch-flow round. Fix: define the "without that field" shape as its own real interface (`IdTokenClaims`) and have the fuller type `extend` it (`IdTokenRecord extends IdTokenClaims { id: string }`), never derive it mechanically.
- **A per-launch/per-request service (e.g. `NamesAndRoles`) takes its scoping data (`platform`, `idtoken`) via the constructor, not as a parameter repeated on every method call** -- established once a `LaunchContext` exists to construct one instance per launch and hand it out already-configured. This also means such a service no longer re-resolves or re-checks things its caller already established: `NamesAndRoles` used to call `PlatformManager.getPlatform()` itself and re-check `active`, but once `OidcService.validateToken()` already resolved and active-checked the platform once (returning it alongside the verified token), redoing that per-service is redundant work, not defense-in-depth -- the dependency (`platformManager`) and the redundant check are removed together, not just the parameter shuffled to the constructor.
- **A pluggable, extensible-in-the-future feature (OIDC `state`) should default to being self-contained wherever persistence isn't actually required for its own sake.** `state` moved from a database row (`StateRecord`, `getState`/`saveState`/`deleteState` on `DatabaseManager`) to a signed, short-lived JWT (`OidcService.buildStateToken`/`verifyStateToken`) once it was recognized that a JWT's signature is already sufficient tamper-evidence and the flow's real replay protection lives elsewhere (the id_token's `nonce`, enforced via `DatabaseManager.saveNonce`/`consumeNonce`, see below) -- removing three interface methods and an entire record type from `DatabaseManager` as a direct consequence of removing a persistence need, not as an independent cleanup.
- **A nonce (or any single-use token) is only genuinely safe to accept if it was actually issued by this server and not yet consumed -- "not seen before" is a weaker, insufficient check on its own.** Introduced in Round 50, per explicit instruction: nonce validation used to be `nonceExists(nonce)` (checked only at id_token-validation time) then `saveNonce(nonce)` on the first sighting -- which silently accepts *any* never-before-seen nonce string, including one this server never generated, not just a genuinely re-issued one. Fixed by saving the nonce at **issuance** time (`OidcService.buildAuthenticationRequestUrl()`, now `async` for exactly this) and atomically checking-and-deleting it at validation time (`DatabaseManager.consumeNonce(nonce): Promise<boolean>`, replacing `nonceExists`) -- a nonce is accepted once and only once, and only if this server actually issued it. The Mongoose nonce TTL (`mongo-schemas.ts`) had to grow from 10 seconds to 600 (matching `OidcService.STATE_TTL_SECONDS`) as a direct, necessary consequence: under the old model a nonce's save-then-check happened within the same request, so a near-instant TTL was enough; under the new model a nonce must survive the full platform round trip (redirect away and back), the same window `state` already budgets for.
- **`LaunchService`'s own OIDC/LTI orchestration logic (`processLoginRequest()`/`processLaunch()`) stays free of any Express/cookies/redirects/session-token concerns, even though the class's public surface (`prepareHttpRoutes()`) isn't framework-agnostic anymore since Round 37.** Those two methods are `private`, called only by the route handlers `prepareHttpRoutes()` registers -- the framework-agnostic *values* they work with (`LoginRequestParams` in, `LoginRequestResult`/`LaunchContext` out) haven't changed, only who's allowed to call them. This is still the boundary between what's built so far and the still-deferred `Provider` core: a future `Provider` constructs `LaunchService` with an `HttpHandler` it owns and calls `LaunchService.prepareHttpRoutes(onLaunch)`, not `processLogin()`/`processLaunch()` directly, since `Provider`'s remaining job (a global callback registry, a ltik-equivalent session token) sits above the route level `prepareHttpRoutes()` already covers, not inside it.
- **An orchestrator service that owns a multi-phase process keeps every phase's step-building logic as its own `private` methods, not split out into sibling pure-function modules.** `LaunchService` owns both halves of a launch (`processLoginRequest()`'s login-initiation and `processLaunch()`'s callback/launch-context creation) as one class -- explicit instruction that "launch" is the entire two-part process, so the class should read as one cohesive thing owning all of it, not delegate part of its own responsibility out to a `login-request.ts`-style module the way the smaller, genuinely-standalone `id-token-parser.ts`/`state-token.ts` pieces are. Default new orchestrator classes to this shape; only pull out a separate pure-function module for logic that's genuinely reusable outside that one class. **This is orthogonal to which *service* owns a step, though**: within `LaunchService`, steps that are genuinely OIDC/LTI-protocol-defined (not launch-application logic) still belong on `OidcService`, not on `LaunchService` itself -- see below. "Don't split into sibling free-function modules" and "delegate protocol-defined logic to the service that owns the protocol" are both true at once; `LaunchService`'s own `private` methods are for launch-application logic it genuinely owns (e.g. `splitTargetLinkUri`), not a catch-all for anything that happens to run during a launch.
- **Steps genuinely defined by the OIDC/LTI spec belong on `OidcService`, even when they're invoked from `LaunchService`'s login-initiation flow.** Building the outgoing OIDC authentication request (`response_type`/`response_mode`/`scope`/`prompt`/`id_token_signed_response_alg` protocol constants, `nonce` generation) moved from `LaunchService` onto `OidcService.buildAuthenticationRequestUrl()` -- the natural counterpart to `OidcService.validateToken()`, which already validates the *incoming* OIDC response. Nonce generation moved with it: `OidcService` already owns the nonce lifecycle on the validation side (`validateNonce`/`saveNonce`), so it should generate the nonce on the request side too, rather than `LaunchService` generating it and handing it over. What stays on `LaunchService`: validating that its own input DTO (`LoginRequestParams`) is complete, and `target_link_uri` query-stashing into `state` -- both are launch-application concerns, not OIDC-protocol operations, even though the field names happen to be OIDC-shaped.
- **`<domain>.serializer.ts` files hold logic that transforms one data shape into another, colocated with that domain's `.service.ts`.** Introduced explicitly in Round 23 (`services/lti/launch/id-token.serializer.ts`, raw `IdTokenRecord` -> the two formatted id_token shapes), meant to be reused for other domains going forward (e.g. a future `memberships.serializer.ts`), not a one-off. Plain exported functions, no class, no injected dependencies; any internal constants are module-level `const`s (no class to own them as fields). Distinct from the "don't split an orchestrator's own steps into sibling pure-function modules" rule below: a serializer isn't an orchestrator's own phase carved off to dodge that rule, it's a named, recurring architectural category in its own right -- when a service's job includes reshaping data from one representation to another, default to giving that reshaping its own `<domain>.serializer.ts` file.
- **A set of literal string constants shared across multiple services/schemas/tests (e.g. namespaced LTI claim keys) belongs in one shared `<domain>.constants.ts` file as a string enum, not duplicated as local `const`s or `private readonly` class fields in every consumer.** Introduced explicitly in Round 26 (`IdTokenClaim` enum, replacing 16 claim-key strings that had drifted into independent copies across five production files and nine test files); moved from `services/database-manager/` to `services/lti/launch/` in Round 31 (see below -- placement of this specific file no longer strictly follows the "layer it describes" rule, by explicit instruction). A string enum (not a plain object of constants) so a member works both as a value (`record[Claim.X]`) and as a computed property key (`[Claim.X]: T` in an interface or object literal), with bracket access through a member narrowing to the exact named-property type rather than falling back to an index signature -- confirmed to hold under this repo's `isolatedModules: true`. Import it `import type` wherever only used in type position, as a value import (`import {...}`) wherever used as a runtime bracket-access or computed-property key. **Placement default**: still prefer the layer/domain a constants file's values actually describe (avoiding a lower layer importing from a higher one) -- but when a shared, zero-dependency constants-only file (no imports of its own, so moving it can never create an import cycle) has an obviously stronger semantic home elsewhere, that's a legitimate reason to place it there instead and accept the resulting reverse import, on a case-by-case basis with explicit confirmation first (see Round 31).
- **Always validate outside/external input with Zod, even where an existing ad hoc check already covers the common case -- but only at the point external input actually enters; don't add a second validation pass over data that's already trusted.** Two gaps closed on this basis: `LaunchService`'s login-route params (an HTTP request's query/body) used to be checked with `params.iss === ''`-style comparisons, which miss a field that's `undefined`/missing entirely, not just empty -- replaced by a real `LoginRequestPayloadSchema` (Zod), with `LoginRequestParams` itself now `z.infer`-derived from it rather than a hand-written interface that could drift. `OidcService.validateToken()`'s decoded id_token payload used to be blindly cast (`as unknown as DecodedToken` in what was then `utils/crypto/crypto.ts`, since split into `shared/utils/crypto/jwt.ts` in Round 48) with zero runtime check that `iss`/`aud`/`iat`/`exp`/`nonce` actually exist and are correctly typed -- the same class of gap that caused the Round 16 `noTimestamp`/`NaN` bug -- closed by `IdTokenPayloadSchema`, validated right after signature verification, before any claim/nonce logic runs. **The corollary, caught during Round 22's review**: `parseIdToken()` (mapping an already-validated `IdTokenRecord` into the formatted `IdToken`) does *not* need a matching `IdTokenSchema` -- by the time it runs, the data has already been validated once going in (`OidcService.validateToken()`) and once again coming out (each `DatabaseManager` implementation validates its own stored record shape before returning it). Nothing untrusted enters the process at that point, so it needs a **type**, not a second runtime **validation** pass -- `IdToken` is a plain hand-written interface (`id-token.types.ts`), like `IdTokenRecord`/`IdTokenClaims` already are, not Zod-derived. Before reaching for `validate<T>(schema, ...)`, check whether the data already crossed a real trust boundary earlier in its lifecycle. **Superseded by Round 39, see below**: a Zod validation failure at any of these boundaries used to be caught and re-thrown as a specific legacy-preserved error string (`MISSING_LOGIN_PARAMETERS`, the 9 claim-error strings, the 3 registration-error strings) -- per explicit instruction, none of that remapping happens anymore; every `ValidationError` is left to propagate directly, uncaught, everywhere in this port. The one exception is `PlatformManager`/`AccessTokenManager`'s handful of plain guard-clause errors (`MISSING_PLATFORM_URL`, `PRIVATE_KEY_NOT_FOUND`, etc.) -- those were never Zod-derived to begin with (single required primitive params, not a structured DTO), so they're unaffected and still throw their own specific `LtijsError` subclass directly.
- **Lowercase file/directory names** throughout `src/` (not the legacy PascalCase `Provider/`, `Utils/`, `Templates/`). Note: this repo's filesystem + git config are case-insensitive (macOS default) — renaming a PascalCase directory to lowercase requires a two-step `git mv` through a temporary name, not a direct rename, and a *new* lowercase directory can never coexist with an old differently-cased one of the same name.
- **Preserve exact legacy error-message strings** (`MISSING_ID_TOKEN`, `PLATFORM_NOT_FOUND`, etc.) wherever a boundary already validated something in the legacy code via a plain guard clause (not Zod) — these are a de facto public contract other code branches on; each has its own typed `LtijsError` subclass (see above) hardcoding that exact string. New validation, and (since Round 39) *any* Zod-schema validation failure regardless of whether legacy had a string for it, gets a `ValidationError` (`src/utils/validation/errors.ts`, moved there in Round 36 alongside `validate()` and extended to `extend LtijsError`) instead, left to propagate uncaught rather than being mapped back onto a legacy string -- see the Zod-validation convention above and Round 39 below for the full reasoning and scope. A shared test helper, `expectValidationErrorOnField(promise, field)` (`test/helpers/expect-validation-error.ts`), asserts a rejected promise threw a `ValidationError` whose `.errors` map contains a given field path, without the `@typescript-eslint/no-unsafe-assignment` errors `.rejects.toMatchObject({errors: {...}})` triggers (Jest doesn't track a rejected promise's error type, so that pattern type-checks against `any`).
- **`got` → `axios`** throughout, via the `RequestHandler` service (`AxiosRequestHandler`). As of Round 43, the shared `httpClient` module (`utils/request/http-client.ts`) is gone entirely -- `AxiosRequestHandler.buildHttpClient()` builds and configures its own bare `axios.create()` instance (just the `HttpError`-normalizing response interceptor, `HttpError` moved to `services/request-handler/errors.ts` and made axios-agnostic in Round 44) directly, since it was the module's only consumer. The legacy `User-Agent: ltijs/<version>` default header is no longer computed inside the implementation at all -- as of Round 46, it's set via the generic `RequestHandler.setPermanentHeader(name, value)` method instead, by whatever composition root eventually resolves the package version.

## Key decisions & rationale (condensed history)

- **Round 1**: set up the whole TS pipeline; ported `NamesAndRoles` as a straight 1:1 class translation to prove the pattern.
- **Round 2**: introduced `RequestHandler` and `AccessTokenHandler`, reworked `NamesAndRoles` to use them with private-method decomposition; switched from native `#fields` to TS `private`/`public`; stubbed the rest of the core trio + remaining services red, test-first.
- **Round 3**: corrected two things after user feedback — (a) classes belong in `services/`, never `utils/`, so `RequestHandler`/`AccessTokenHandler`/`Database` moved out of `utils/`; (b) types must be pure data, so the `Platform` *class* was deleted entirely and replaced by a plain `Platform` type + a new `PlatformManager` service owning all platform operations. Also renamed `Grade` → `Grading`, and relocated the `Platform` type from a `shared/` file into `platform-manager.types.ts` (colocated with its owning service) after further feedback.
- **Round 4**: replaced the generic `Database`/`DatabaseAdapter` (five methods parameterized by a `collection` string + an `ENCRYPTIONKEY` override, mirroring legacy `Database.js` 1:1) with a `DatabaseManager` interface — one specific, purpose-named method per actual DB operation used across the codebase, exported for library users to implement their own. Per explicit user decisions: (a) `ENCRYPTIONKEY` was stripped from every method and cascaded out of every already-built signature that only had it to thread through (`PlatformManager`, `AccessTokenHandler`, `Auth`'s stubs) — encryption is now purely an implementation detail of one specific implementation; (b) both concrete implementations were fully built this round, not stubbed: `MongoDatabaseManager` (new default, encrypts nothing) and `MongoLegacyDatabaseManager` (`extends` the former, encrypts the same three collections `Database.js` always did — `publickey`/`privatekey`/`accesstoken` — via a constructor `ENCRYPTIONKEY`, for existing deployments; every other collection was never encrypted even in the legacy code). Added a shared `test/helpers/build-fake-database-manager.ts` in-memory fake (via a new `@test/*` path alias) to replace the ad hoc fakes `PlatformManager`'s and `AccessTokenHandler`'s test files had each hand-rolled. Also surfaced and fixed two real bugs during DB-integration testing: Mongoose mutates (adds `__v`, etc. to) a plain object passed directly as a write document, so `DatabaseManager` methods now clone caller-owned records before writing; and re-`setup()`-ing accumulated `mongoose.connection` listeners across instances, fixed by clearing them at the start of `setup()` plus an explicit `mongoose.disconnect()` in each `.dbtest.ts` file's `afterAll`.
- **Round 5**: applied the same interface-plus-default-implementation shape `DatabaseManager` established to the two remaining cross-cutting concerns. `RequestHandler` (the concrete axios-backed class) split into a `RequestHandler` interface (`request-handler.types.ts`) + `AxiosRequestHandler` implementation (renamed from `request-handler.service.ts`); consumers now depend on the interface type. New `Logger` interface (`log(level, component, message)`, levels `'debug' | 'info' | 'warn' | 'error'`) + `DebugLogger` implementation wrapping the `debug` package exactly like every legacy module already did individually (one cached `debug.Debugger` per component, namespaced `provider:<component>`) — this replaces `NamesAndRoles`'s direct `createDebug()` import with an injected `logger`. Both interfaces were wired into every already-implemented (green) service as an optional trailing constructor param defaulting to a shared instance (`AccessTokenHandler`, `PlatformManager`, `NamesAndRoles`, `MongoDatabaseManager`/`MongoLegacyDatabaseManager`); the still-red stubs (`Grading`, `DeepLinking`, `DynamicRegistration`, `Auth`) got only a mechanical import-path fix where they referenced the renamed `RequestHandler` module, per explicit user decision to scope Logger/interface wiring to real implementations only. `MongoDatabaseManager`'s `setup()` gained the connection-lifecycle log lines (`connected`/`open`/`reconnected`/`disconnected`/reconnect-error) that legacy `Database.js` always had but the TS port's `setup()` was previously silent on.
- **Round 6**: reconciled `NamesAndRoles` against `PlatformManager`/`AccessTokenHandler`, per explicit user instruction after noticing its constructor still took the pre-`PlatformManager` `getPlatform`/`ENCRYPTIONKEY`/`Database: unknown` shape (`shared/platform-like.types.ts`'s `GetPlatform`/`PlatformLike`, flagged as deferred reconciliation work since Round 3). `NamesAndRoles`'s constructor now takes exactly `DatabaseManager`, `RequestHandler`, `Logger` -- no `getPlatform` function, no `ENCRYPTIONKEY` -- and composes its own internal `PlatformManager`/`AccessTokenHandler` from those three. `resolveActivePlatform()` calls `platformManager.getPlatform()` and returns the plain `Platform` type instead of the method-shaped `PlatformLike`; `getMembers()` calls `accessTokenHandler.getAccessToken()` instead of `platform.platformAccessToken()`. Scoped to `NamesAndRoles` only -- `Grading`/`DeepLinking`/`DynamicRegistration` are still red stubs and stay on `GetPlatform`/`PlatformLike` until they're actually implemented, matching the stub-scoping already used in Round 5. `shared/platform-like.types.ts` is not deleted, since those three still depend on it.
- **Round 7**: removed every constructor default value across every service, per explicit user instruction that "things like `defaultRequestHandler` should not be defined/used" -- services just require their dependencies and store them as `private`, full stop. Confirmed to apply uniformly, not just to `RequestHandler`/`Logger`: `PlatformManager`'s `generateKeyPair` and `AxiosRequestHandler`'s own `AxiosInstance` param lost their defaults too, and the still-red stub constructors (`Grading`, `DynamicRegistration`) got the same mechanical fix so the whole codebase settled on one DI convention. `AxiosRequestHandler`/`DebugLogger` also lost their pre-built shared-instance exports (`export const requestHandler = ...`, `export const logger = ...`) entirely -- each module now exports only its class. Building real implementations together becomes the job of a centralized construction point, deliberately not built this round (`TBD`); until it exists, every call site (including every test) constructs and passes its dependencies explicitly, which directly improves testability (a test's actual dependencies are now visible at its own call site instead of hidden behind a class-level default). Also revisited Round 6's `NamesAndRoles` shape: rather than taking a raw `DatabaseManager` and building its own private `PlatformManager`/`AccessTokenHandler` internally, it now takes **already-constructed** `PlatformManager`/`AccessTokenHandler` instances directly as constructor params, per explicit user instruction ("services receive dependencies already implemented") -- avoids `NamesAndRoles` silently constructing redundant, un-shared copies of services the future centralized place will build once and share across `NamesAndRoles`/`Grading`/`DeepLinking`/`DynamicRegistration`.
- **Round 8**: two small logging-cleanliness fixes, spotted while looking at `NamesAndRoles`. `Logger.log()`'s level was always a raw string literal (`'debug'`, `'error'`) at every call site -- `logger.types.ts` now exports a capitalized `LOG_LEVELS` const (`DEBUG`/`INFO`/`WARN`/`ERROR`), with `LogLevel` derived from it as the single source of truth. Separately, `NamesAndRoles` was the only service that named its log component at all, and even then as a module-level `const LOG_COMPONENT` sitting outside the class rather than a class member; `AccessTokenHandler`/`PlatformManager`/`MongoDatabaseManager` had the same underlying problem in a worse form (a bare string literal repeated inline at every call site, no name at all). All four now have a `private readonly LOG_COMPONENT` class field instead. (Superseded in Round 10 -- see below.)
- **Round 9**: extended Round 8's field-not-module-constant principle to non-logging constants: `NamesAndRoles`'s `NRPS_SCOPE`/`NRPS_ACCEPT` and `AccessTokenHandler`'s `CLIENT_ASSERTION_TYPE` moved from module-level `const`s into `private readonly` class fields, per explicit instruction that a service's own constants belong on the class (`public readonly` only if something outside the class genuinely needs them).
- **Round 10**: `Logger.log(level, component, message)` became three dedicated methods -- `debug(component, message)`, `warn(component, message)`, `error(component, message)` -- per explicit instruction, so the level is which method you call rather than a string argument. `LogLevel`/`LOG_LEVELS` (introduced in Round 8) are deleted entirely as a result -- no longer needed once there's no level parameter to type. `info` was deliberately not given a method: a grep across the whole codebase confirmed nothing ever logged at `info`, only `debug`/`error` were in real use (`warn` wasn't either, but was one of the three explicitly requested). `DebugLogger`'s three public methods share one private `write(component, level, message)` helper internally, so the `debug`-package formatting/caching logic is unchanged.
- **Round 11**: reorganized `NamesAndRoles`'s pagination `do`/`while` loop per explicit instruction, decomposing it into an atomic `fetchPage(pageUrl, query, accessToken)` (single-page fetch) driving `fetchPages()` (the full loop) -- `getMembers()`'s old `initialNext` renamed `initialPage`, and the fetched-page shape renamed from `body` to `memberships` (user correction mid-review) inside a new `MembershipsPage { memberships, next, differences }` type (`names-and-roles.types.ts`, replacing an inline `InitialRequest` interface, itself renamed `MembershipsRequest`).
- **Round 12**: added a service-specific `ensureServiceAvailability(idtoken)` guard to `NamesAndRoles.getMembers()`, per explicit instruction to establish the pattern for other services later. Landed alongside a signature change (also explicit instruction): `getMembers()`'s `idtoken` became a required param (not optional), with the guard reading `idtoken?.platformContext?.namesRoles?.context_memberships_url` (the `?.` defensive against non-TS-compliant callers, not the type system) instead of a separate `MISSING_ID_TOKEN` null-check. Codified as a standing convention (see above) for `Grading`/`DeepLinking`/`DynamicRegistration` to follow once implemented.
- **Round 13**: removed `PlatformManager.getPlatform()`/`registerPlatform()`'s per-call `databaseManager` override parameter, per explicit instruction to identify why it existed or remove it. Root cause (confirmed by inspecting the legacy code): `Provider.getPlatform` used to be passed around as an unbound function reference, so implementations needed a way to thread the right `Database` instance through per-call; `PlatformManager` is constructor-injected and always called as a proper bound method, so the override was dead legacy weight, not a real requirement -- `GetPlatformFn` dropped the param from both overload signatures.
- **Round 14** (largest round yet): full three-layer record refinement of `DatabaseManager`, per explicit, detailed instruction to stop letting Mongo's own table structure leak into the interface. `database-manager.schemas.ts` deleted; `database-manager.types.ts` is now plain hand-written types (18 methods, down from 29). Platform status and keys merged into `PlatformRecord`/`Platform` as plain fields (`active`/`publicKey`/`privateKey`), eliminating 11 interface methods (`getPlatformStatus` et al., all 8 key methods) -- confirmed with the user first via explicit question (`Platform` never leaves the process, so a fetched platform should always carry its keys). Renamed `accesstokenEndpoint`→`accessTokenEndpoint` and `authConfig`→`idtokenValidation` at the interface and service levels, with the old names kept as same-value aliases on the service-level `Platform`/`PlatformRegistrationInput`/`PlatformUpdateInput` for backward compatibility. `IdTokenRecord`/`ContextTokenRecord` unified into one `IdTokenRecord` shaped like the raw id_token claims (literal namespaced keys, confirmed via explicit question to use this over a "clean" camelCase shape, matching ltiaas-node's `RawIdTokenSchema`) -- `clientId`/`platformId` stay as resolved (non-raw) fields as before. `GenerateKeyPairFn` now returns `Promise<GeneratedKeyPair>` (`{kid, publicKey, privateKey}`) instead of just a kid string, since key persistence is no longer a `DatabaseManager` method it can call itself; `PlatformManager.createNewPlatform()` embeds the returned keys directly into the record it creates, and `toPlatform()` (renamed from `buildPlatform`) became a synchronous pure mapping function (no more per-fetch DB round-trip for status). `MongoLegacyDatabaseManager` gained substantial new override logic to keep satisfying the unified interface from the real, unchanged legacy collection layout (see status table above). Two real technical obstacles were hit and resolved via explicit user decisions during implementation, not silently patched around: (1) the legacy `idtoken`/`contexttoken` collections never persisted `aud`/`exp`/`iat`/`nonce` (transient, JWT-validation-only fields) -- made optional on the interface rather than fabricated; (2) storing `IdTokenRecord`'s literal dotted claim keys as flat Mongo document fields breaks both Mongoose's Document layer (always splits a top-level dot into a nested path, even with `strict: false`) and MongoDB's own query-filter syntax (a dot in a filter key is always nested-path notation, never literal) -- resolved by having `MongoDatabaseManager` read/write the `idtoken`s collection via the native MongoDB driver instead of a Mongoose Model (fixes storage), and by adding a clean top-level `deploymentId` field to `IdTokenRecord` alongside the raw claim key (fixes querying), both now standing conventions (see above).
- **Round 15**: several small follow-up corrections after Round 14, each per explicit user instruction. `MongoConnectionConfig` moved out of `database-manager.types.ts` (the implementation-agnostic interface file) into a new `mongo/mongo-database-manager.types.ts`, since it's pure Mongoose connection config no other implementation would ever use. `saveState(state, query)` changed to `saveState(record: StateRecord)`, matching `saveIdToken`'s already-established pattern of deriving the upsert key from the record itself instead of taking it as a separate loose param, once it was pointed out `StateRecord` already carries its own natural key (`state`). `MongoLegacyDatabaseManager`'s 14 module-level namespaced-claim-key constants moved into `private readonly` class fields, per the long-standing "service-internal constants are class fields, not module constants" convention this file itself documents but the DatabaseManager round had violated. Finally, `services/database-manager/mongo-schemas.ts` (shared between both Mongo implementations since Round 4) was split into `mongo/mongo-schemas.ts` and `mongo-legacy/mongo-legacy-schemas.ts`, each implementation moved into its own eponymous subfolder -- explicit instruction that the two implementations should never share a schema module, since their document shapes are independently owned even though `MongoLegacyDatabaseManager extends MongoDatabaseManager`. The two collection names both implementations deliberately target for real (`platform`/`idtoken`) are the one thing `mongo-legacy/`'s schema module still imports from `mongo/`'s, as plain exported string constants (`PLATFORM_COLLECTION`/`IDTOKEN_COLLECTION`), not schema/model objects.

- **Round 16** (launch flow -- second-largest round yet): built the HTTP-framework-agnostic heart of an LTI launch, per an explicit, detailed request covering `LaunchService`/`LaunchContext`, opaque id_token IDs, and JWT-based `state`. Confirmed via explicit user decisions during planning: `LaunchContext` receives already-constructed `PlatformManager`/`AccessTokenHandler` (shared across launches, built once); `MongoLegacyDatabaseManager` generates a random opaque ID stored as a new `launchId` field; `LaunchContext` wires up `NamesAndRoles` only this round (`Grading`/`DeepLinking` stay on the old shape until each is implemented); JWK→PEM conversion uses Node's built-in `crypto.createPublicKey`, not `rasha`. Mid-implementation, the user redirected the plan further: **`utils/auth/` renamed to `utils/crypto/` and narrowed to pure cryptographic primitives, with the OIDC/LTI validation orchestration (platform lookup, claim/nonce checks) pulled out into a new `OidcService` class** -- `Auth`'s 21 red tests were redistributed into green `crypto.test.ts` + `oidc.service.test.ts` coverage against the class API, and `generatePlatformKeyPair` alone stayed a red stub (unrelated to the launch flow). `DatabaseManager.getIdToken`/`saveIdToken` changed from a 4-param natural-key lookup to a single opaque `id` the implementation itself decides (`MongoDatabaseManager` uses Mongo's own `_id`; `MongoLegacyDatabaseManager` generates a `launchId`) -- `state`/`StateRecord`/`getState`/`saveState`/`deleteState` deleted from `DatabaseManager` entirely, replaced by a signed JWT (`services/launch/state-token.ts`, a standalone pure-function module at the time -- folded into `OidcService` in Round 21) needing no persistence. `NamesAndRoles` lost its `platformManager` dependency entirely (not just relocated) once `OidcService` started handing back an already-resolved, already-active-checked `Platform` -- its own `resolveActivePlatform()`/`PLATFORM_NOT_FOUND`/`PLATFORM_NOT_ACTIVATED` checks were redundant, not defense-in-depth, and were removed. Two real technical obstacles were hit and resolved, not silently patched around: (1) `Omit<IdTokenRecord, 'id'>` silently collapsed every named property down to the index signature's `unknown` when spread (confirmed via an isolated repro) -- fixed by introducing a real `IdTokenClaims` interface `IdTokenRecord` `extends`, never deriving "record minus a field" mechanically from an indexed interface again (now a standing convention); (2) `jsonwebtoken`'s `noTimestamp: true` doesn't just skip auto-setting `iat`, it deletes a caller-supplied `iat` too, discovered when a `TOKEN_TOO_OLD` test silently passed on a `NaN` comparison -- fixed by dropping `noTimestamp` entirely, since `jsonwebtoken` already respects an `iat` already present in the payload.

- **Round 17**: removed `PlatformManager.registerPlatform()`'s leftover `getPlatform?: GetPlatformFn` override parameter (and the private `modifyRegisteredPlatform()`'s matching one), per explicit instruction to go through the services and remove any remaining "old design" `getPlatform` override params -- the same unbound-function-reference workaround Round 13 already removed from `getPlatform()` itself had survived on `registerPlatform()`. Both methods now always call `this.getPlatform(...)` directly; the now-fully-dead `GetPlatformFn` type was deleted from `platform-manager.types.ts`. A codebase-wide grep confirmed the only other `getPlatform`-as-parameter instances are `Grading`/`DeepLinking`/`DynamicRegistration`'s constructor-level `getPlatform: GetPlatform` (the old `@shared/platform-like.types.ts` shape) -- structurally different (their sole platform-lookup mechanism, predating `PlatformManager`'s existence entirely, not a redundant override alongside a real dependency) and left as the already-documented deferred reconciliation in the Roadmap section above, not touched this round.
- **Round 18**: `LaunchService` gained the login-initiation half of a launch, per explicit instruction that it should own the *entire* two-part process (not just the callback half built in Round 16).
